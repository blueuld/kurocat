## 1. 问题

「鼠标悬停让位」功能上线后，用户反馈：**鼠标移到猫伸出去的爪子和尾巴上时，猫不会淡化**。截图标注了两处：

- 右侧：甩到身侧的尾巴尖
- 左侧：抬起敲键盘的爪子

猫身正中间、键盘区域正常，说明功能本身没问题，是**判定区域没有覆盖整只猫的可见轮廓**。

---

## 2. 原实现

悬停判定在主进程的命中循环里，每约 150ms 取一次光标位置：

```rust
// 简化后的调用链
let pet_rx = (rx - pet_x0) / pet_w_frac;   // 换算到「宠物矩形」内归一化
let pet_ry = (ry - pet_y0) / pet_h_frac;
let (over_interactive, raw_over_cat) =
    is_over_interactive_silhouette(pet_rx, pet_ry, is_108);
```

```rust
fn is_over_interactive_silhouette(rx: f64, ry: f64, is_108: bool) -> (bool, bool) {
    let (cat_cx, cat_rx) = if is_108 { (0.51, 0.21) } else { (0.48, 0.25) };
    let dx_cat = (rx - cat_cx) / cat_rx;
    let dy_cat = (ry - 0.49) / 0.27;
    let over_cat = (dx_cat * dx_cat + dy_cat * dy_cat) <= 1.0;   // 猫身椭圆

    let over_desk = if is_108 {
        rx >= 0.04 && rx <= 0.94 && ry >= 0.65 && ry <= 0.94      // 键盘/鼠标
    } else {
        rx >= 0.06 && rx <= 0.92 && ry >= 0.65 && ry <= 0.91
    };

    (over_cat || over_desk, over_cat)
}
```

即：**一个窄椭圆（猫身）+ 一个下部矩形（键鼠）**。椭圆在水平方向最多覆盖到 x≈0.72，竖直方向从 y≈0.22 开始，因此尾巴尖和耳尖天然落在外面。

## 3. 诊断方法（可复用的标定流程）

没有靠肉眼估坐标，而是先建立两套度量再对比。

### 3.1 坐标系换算

| 事实 | 值 |
|---|---|
| 基准尺寸（108 键） | 540 × 456 |
| 用户缩放 | 0.6 |
| 窗口逻辑尺寸 | `base × scale` = 324 × 274 |
| 宠物矩形占比 | `pet_w_frac = pet_h_frac = 1.0`（窗口恰好等于宠物矩形） |
| 实际 DPI | 150%（页面截图 486×411 = 窗口 × 1.5） |

结论：本例中**窗口归一化坐标 ≡ 宠物矩形归一化坐标**，且对缩放不敏感（精灵是等比缩放的），所以从截图量出的比例可以直接写进代码。

## 4. 修改

`src-tauri/src/lib.rs` → `is_over_interactive_silhouette`，在原有椭圆与键鼠矩形之外补三块：

```rust
// 65% 布局下整只猫相对 108 键略偏左，补一个水平偏移，下面的补充区域共用。
let x_shift = if is_108 { 0.0 } else { -0.03 };

// 耳尖与头顶：竖直方向椭圆够不到（实测 y 0.17~0.25 的那一截），单独补一块。
let over_head_top = (0.29 + x_shift..=0.73 + x_shift).contains(&rx)
    && (0.13..=0.30).contains(&ry);

// 甩到身侧的尾巴：实测在 x 0.62~0.80、y 0.44~0.62，椭圆只覆盖到 0.72，会漏掉尾尖。
let dx_tail = (rx - (0.72 + x_shift)) / 0.14;
let dy_tail = (ry - 0.53) / 0.11;
let over_tail = (dx_tail * dx_tail + dy_tail * dy_tail) <= 1.0;

// 伸出去的爪子：左爪常抬起敲键盘，会从身体左侧探出一段（实测 x 0.10~0.21, y 0.67~0.79）。
let over_paw = (ry >= 0.56 && ry <= 0.82) && (rx >= 0.04 + x_shift && rx <= 0.34 + x_shift);

// 只有猫身椭圆算「撸猫」目标；其余区域仅用于悬停让位与点击命中。
let over_any = over_cat || over_head_top || over_tail || over_paw || over_desk;
(over_any, over_cat)
```

### 设计要点

| 点 | 说明 |
|---|---|
| 返回值语义不变 | 第一个值 `over_interactive` 同时决定「是否触发淡化」与「是否接管点击」；第二个 `over_cat` 决定「能不能撸猫」 |
| 撸猫范围不变 | 仍是猫身椭圆，尾巴上不会误触发踩奶/眯眼动作 |
| 缩放无关 | 全部用宠物矩形内归一化坐标，20%–150% 缩放行为一致 |
| 布局兼容 | 65% 布局整体 `x_shift = -0.03` |

## 6. 采样抖动的坑（重要）

验证过程中出现过「明明在猫身上却判不触发」的假阴性，原因不是代码：

- 命中轮询间隔约 150ms；用户设置里淡化延迟 500ms
- 单点停留 620–850ms 时，若主线程某次轮询被推迟，就可能整段错过

**结论：验证时每点停留 ≥1.2s 才稳定。** 上文的 15×12 终检即为 1.25s 采样，结果与水平细扫一致。

## 10. 已知边界

1. **尾巴是动画的**：尾巴摆动幅度更大时，尾尖可能超出当前椭圆（中心 0.72、横向半径 0.14）。若后续复现漏判，把 `over_tail` 的横向半径加到 0.16–0.17 即可。
2. **耳朵姿态变化**：飞机耳（生气）时耳朵向内收，不影响覆盖；好奇/警觉姿态耳朵可能抬高约 2%，`over_head_top` 的 y 下界 0.13 留有余量。
3. **65% 布局仅做几何平移**，未逐像素重新标定；若在该布局下发现偏移，按同法重扫一次即可得到精确 `x_shift`。
4. **命中区域同时决定点击接管**：这是有意为之——可见部位本就该接收点击。透明区域的多余覆盖只影响悬停后 500ms 内的点击归属。

## 11. 2026-11-27 回归：上游「不透明度」让淡出完全失效（v5.2.5 修复）

### 现象

升级到 v5.2.3 / v5.2.4 后，鼠标停在猫身上不再淡化、也不让出点击。本机配置为
`hoverFade=true`、`hoverFadeDelayMs=500`、`hoverFadeOpacity=0.1`、`clickThroughLocked=true`、`renderMode=3d`。

### 排查结论

后端链路**全部完好**，逐项核对过：

| 环节 | 位置 | 状态 |
|---|---|---|
| 判定 | `lib.rs` `if hover_fade && over_interactive && !is_drag` | 在，且不受 `effective_locked` 影响 |
| 事件 | `app.emit("kuro-hover-fade", {active, opacity})` | 在 |
| 点击穿透 | `should_ignore` 的 `else if hover_hidden { true }` | 在 |
| 配置映射 | `config.rs` `#[serde(rename_all = "camelCase")]` | 在 |
| 前端监听 | `main.ts` `listen('kuro-hover-fade')` → 设置 CSS 变量 + body class | 在 |
| 掩码采样 | `SilhouetteSampler` → `set_pet_mask` | 在 |

关键对比（用 `git diff 7b34f50 HEAD`）：

- 旧版 `7b34f50` 的 `main.ts` **没有任何** `canvas.style.opacity` 写入，所以无 `!important` 的 CSS 淡化规则能正常生效；
- 上游 9 个提交合并后新增 `applyPetOpacity()`（5 处调用），直接写 `canvas.style.opacity = ...` / `canvas3d.style.opacity = ...`。**内联样式优先级高于普通选择器**，于是 `body.pet-hover-fade #pet-canvas { opacity: var(--pet-fade-opacity) }` 被内联的 `1` 盖掉 —— 淡出在视觉上彻底失效。

### 修复（v5.2.5）

1. `src/style.css`：淡化规则加 `!important`，让淡出成为 opacity 的最终权威。
2. `src/main.ts`：`kuro-hover-fade` 监听里同步接管内联值 —— `active` 时把两个 canvas 的内联 opacity 设成 fade 值，恢复时调 `applyPetOpacity(settings.opacity)` 回到用户设置的基础不透明度。避免淡出期间其他设置事件把内联重置成 1。

两处是双保险：CSS 负责最终生效，JS 负责让恢复干净、computed 值一致。

### 验证状态

- `npm run build` 通过（产物 CSS 实测含 `body.pet-hover-fade ... {opacity:var(--pet-fade-opacity, .12)!important}`）。
- CI run `45933193266` = success（3 分 20 秒），构建提交 `0e6f596`；Release v5.2.5 的 tag 指向该提交，
  `KuroCat-5.2.5-windows-x64.exe` 5,185,024 字节，sha256 `7166ce5d…2368`。
- **运行时逐点扫描未做**：当前运行实例没有开 9222 调试端口，不打断用户会话去重启。安装 v5.2.5 后可按第 9 节复现步骤验证：

## 12. Alt 临时解除淡出 + 与穿透锁定互斥（v5.2.8）

### 需求与约束

- 上游已有「按住 Alt 临时解除穿透锁定」，本次给淡出加**同语义**的 Alt 临时解除：按住 Alt 期间不淡出、松开后重新计时。不改上游穿透锁定功能。
- 穿透锁定与悬停淡出不能同时打开；冲突时**拒绝本次开启**（不改用户配置），并给猫咪拟人文案提示：设置菜单内文字条、主窗右键菜单用猫旁气泡。

### 实现

1. **Alt 临时解除淡出**：`lib.rs` 的淡出判定改为
   `if hover_fade && !effective_locked && over_interactive && !is_drag && !alt_override`。
   - `alt_override` 来自 `input_hook::is_alt_pressed()`（Windows `GetAsyncKeyState(VK_MENU)` + 键盘钩子兜底），与上游穿透锁定**共用同一状态**。
   - 上游 `effective_locked = locked && !alt_override` 一行未改。
   - 松开 Alt 后 `hover_since` 已清空，因此按原延迟重新计时，不会瞬间又淡出。
2. **互斥运行时兜底**：`!effective_locked` 确保穿透实际生效时不再叠加淡出；只在运行时判定，不写 `settings.json`。
3. **前端拦截**：
   - `menuMain.ts`：开淡出时若穿透已锁定、或开穿透时若淡出已开 → 拒绝本次 patch、保持菜单打开并显示提示条。
   - `main.ts` 右键菜单 `toggle-lock` 走同一规则，用现有 `showUpdateToast` 显示同一句文案。
   - `menu.html` + `style.css`：新增琥珀色 `mode-conflict-toast`，3.6 秒自动消失。
4. **i18n**：5 个 locales 增加 `mode_conflict_fade`、`mode_conflict_lock`、`hover_fade_alt_hint`；中文文案示例：「猫猫分身乏术～隐身术和铁布衫只能选一个，先收起铁布衫吧！」
